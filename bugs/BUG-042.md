## Описание

После исправления BUG-037 в `ProfileViewModel` (устранения side effect из `combine`) введён промежуточный `_profileFlow`:

```kotlin
private val _profileFlow = getUserProfileUseCase()
    .onEach { profile -> _latestProfile.value = profile }
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5_000),
        initialValue = null,
    )
```

`_profileFlow` имеет `initialValue = null`. Когда `combine` использует `_profileFlow` вместо прямого вызова `getUserProfileUseCase()`, он получает дополнительное промежуточное событие с `profile = null` (начальное значение `stateIn`).

Это ломает существующий тест `loadProfile_returnsCorrectState` в `ProfileViewModelTest`:

- Тест ожидает 2 события: `isLoading = true` → `isLoading = false` с `userName = "Алексей"`
- Фактически происходит 3 события: `isLoading = true` → `isLoading = false, userName = ""` (profile = null) → `isLoading = false, userName = "Алексей"`
- Тест получает на втором `awaitItem()` состояние с `userName = ""` вместо `"Алексей"`, что приводит к провалу `assertEquals("Алексей", loaded.userName)`

## Возможная причина

`_profileFlow` объявлен с `initialValue = null`. При подписке `combine` на `_profileFlow` немедленно получает `null` как первое значение, что приводит к промежуточному emit в `uiState` с `profile?.name.orEmpty() = ""`. Тест `loadProfile_returnsCorrectState` не учитывает этот дополнительный emit.

Варианты исправления:
1. Обновить тест — добавить `awaitItem()` для промежуточного null-состояния.
2. Изменить подход в ViewModel — использовать `getUserProfileUseCase()` как обычный `Flow` через `onEach` без `stateIn`, чтобы не создавать промежуточное `null`-состояние.
